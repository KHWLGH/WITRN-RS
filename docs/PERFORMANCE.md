# 性能基准与边界

本文记录可重复的算法、存储、启动和发货形状基准。它用于评估性能优化，不把浏览器帧率或真机长跑当作每次改动的自动回归。

## 测量范围

| 基准 | 命令 | 关注点 |
| --- | --- | --- |
| 核心算法 | `node bench/core.mjs` | 列存储、分桶、范围统计、能量积分 |
| 算法阶段对照 | `node bench/phase2.mjs` | 范围统计和协作切片的前后版本对照 |
| 存储阶段对照 | `node bench/phase3.mjs` | 分块存储、统计和能量计算的前后版本对照 |
| 算法对照 | `node bench/extrema.mjs` | 逐样本扫描与极值索引 |
| 启动 | `node bench/startup.mjs` | 原生二进制启动分段和资源形状 |
| 发货形状 | `node bench/packaging.mjs` | `out/` 文件集合、阻塞资源和孤儿资产 |
| Rust | `cargo bench -p lapower` | 协议解码、编码、选择路径 |

`bench/core.mjs --compare` 使用 `bench/baselines/` 中的输入指纹和指标集合进行多轮对照；`--verify-baseline` 只运行一次数据正确性检查，并校验输入指纹、指标集合、重复次数和轮次设置，不执行预热、性能计时或计时阈值判断，适合 CI。共享 runner 的绝对耗时会受频率、负载和缓存影响，单次耗时只作为报告，不直接升级为发布门禁。

## 前端产物

`npm run build` 将 `src/` 镜像到 `out/`，并在 `out/` 内合并阻塞样式表；开发模式保留原生 JavaScript 模块。`npm run build:dist` 的发布模式进一步把应用入口、两个 CSV Worker、PD 导出 Worker 和范围统计 Worker 分别合并，保留 Worker 文件名并移除已合并的模块。`node scripts/build-dist.mjs --bundle-js` 可生成未压缩的合并版本，用于启动对照。typecheck 与 Node 核心测试继续使用 `src/` 中的源模块。`bench/packaging.mjs` 检查：

- `out/` 中从源码镜像的文件都已跟踪；合并脚本、样式与从 `src-tauri/icons/` 复制的关于页图标由构建生成；
- 声明文件和点号目录不会进入发货集合；
- `index.html` 不含内联脚本，资源引用可以解析；
- 没有新的已跟踪孤儿资产。

这些是确定性发货不变量，适合固定在 `perf-shape` CI job 中。

## 存储与数据完整性

分块列存储以 4096 点为块，避免连续数组扩容时整列复制。性能评估应同时记录范围统计、能量积分、追加边界和容量变化，并用现有 `chart-*`、`range-stats`、`recording` 和 `recording-spool` 核心测试确认结果不变。

每点保存实际采样间隔；CSV 在末尾追加可选的 `SampleInterval(ms)`，混合采样率按逐点间隔判定积分空档。旧文件继续使用摘要间隔、时间序列估算和绝对 2 秒保护。12 列原始数据与辅助索引按约 112 字节/点估算，CSV 按约 128 字节/行估算。

恢复文件的表头立即同步，Rust 每秒刷新缓冲并唤醒前端排空、回写表头；大回填每轮只捕获一次固定快照，写入途中也检查同步期限。失败时保留恢复文件；仅成功同步的正常收尾删除它。扫描兼容历史碰撞名称 `stem.partial-2.csv`。

密集跟随投影允许自然追加期间完成固定快照，按该快照的 X 范围提交，再处理最新窗口；隐藏监控页时取消准备。大范围统计使用 Worker 按原顺序折叠，每次转移最多 4096 行的副本；同一窗口最多一个活动任务，计算启动间隔为 `max(250 ms, 上次完整计算耗时 × 4)`。更新期间显示已完成范围及其边界，Worker 不可用时回退到协作分片。PD 导出每批最多 128 条报文，在 Worker 中格式化并按写入确认推进，单块最多 1 MiB，保持 v2 文件和 v1 元数据兼容。

CSV、采集、录制和协议解析的性能优化优先复用现有核心测试与基准。只有发现数据损坏、协议不兼容、崩溃/死锁或已确认的高影响回归时，才新增针对性测试或基准。

## 密集图表显示预算

原始列始终完整保留。主图默认每 2 个 CSS 像素一个 min/max 桶，内部档位为 1、2、4、8、16 像素，桶预算至少 64。样本数/桶取 2 的幂，使全历史增长和降密度可以通过合并相邻桶完成；合并和同密度重建逐值一致，包括 NaN、正负零和未满尾桶。放大到点数不超过绘图区 CSS 宽度的窗口时恢复原始点，光标仍查原始样本。

导航缩略图同样使用每 2 个 CSS 像素一个桶的固定预算，避免主图降密度后，缩略图仍提交过多顶点。其预算从约 4 个顶点/CSS 像素降为约 1 个；单点功率峰值与未满尾桶的最新时间保留，并由绑定回归测试验证。

显示分桶与阴影保护采用独立规则：可见点数超过绘图区 CSS 宽度时可进入分桶，但面积填充默认保留。达到 4 点/CSS 像素才有关闭阴影的资格（600 CSS px 至少约 2400 点），达到资格仍不会自动关闭。普通慢帧先确认并降低显示密度；实际绘制过降低后的密度、又出现连续两次慢帧，才关闭阴影。已达最粗密度时，两次慢帧也可触发保护；单次超过 100 ms 的严重绘制延迟允许直接关闭。每次刷新新增点数超过 4×绘图区宽度只标识大批次压力，健康批次不会关闭阴影。该策略统一用于实时录制、暂停和 CSV 回看，不按请求采样率或累计记录时长设置硬开关。阴影反馈仅计算实际绘制耗时及绘制结束后的帧延迟，排除导入、列初始化和协作冷建在绘制前的耗时，避免长历史误判。

恢复阴影需要连续两秒健康绘制，并距离上次关闭至少五秒，以免频繁闪烁。页面隐藏、数据源替换、用户窗口变化、窗口低于阴影候选阈值或用户调整填充/通道显隐时清除旧阴影反馈；实时全历史/跟随窗口的自然追加保留证据。用户设置为 0 的通道始终关闭填充；静止回看不为累计恢复时间创建无限重绘。同一密度下，拖动和松手遵循相同投影规则，不另建预览投影。超过 32768 点的准备采用协作切片：每步最多处理 4096 点，每片预算 1.5 ms，完整投影完成后再提交；数据源、窗口或密度变化会取消过期任务。

`drawClear` 到 `draw` 只反映 JS 绘制耗时，不能代表 Canvas 栅格化结束。控制器同时观察 `draw` 到下一次 rAF 的延迟，以及该绘图请求以来已经完成的帧间隔，避免遗漏延后发生的栅格化阻塞。空闲基线取最近 32 个候选帧间隔的第 20 百分位，排除包含图表绘制的帧，防止慢帧抬高基线。超过 `max(33 ms, 空闲帧间隔 × 2)` 两次降一档，单次超过 100 ms 降两档；连续稳定两秒后尝试恢复，每五秒最多恢复一次。后台、稀疏或中断的反馈不能累计恢复时间。密集窗口（实时与回看）最多观察绘制后的三个 rAF，将这段窗口的最大延迟作为一个绘制样本，避免快速的首次回调漏掉延后出现的 Canvas 阻塞，也不把同一个停顿重复算作连续慢帧。首次一般慢帧排一次确认重绘；健康结果停止，第二个慢绘制降低密度，达到最粗档位后不再自动重绘。回看窗口或数据源变化、页面隐藏时取消旧观察与确认任务。密集实时主图结合准备、绘制和帧延迟在 33–100 ms 间调节刷新间隔；回看交互不使用实时节流。

`window.__WITRN_PERF__()` 的 `charts.main.last` 增加 `sourcePointCount`、`displayPointCount`、`pixelsPerBucket`、`displayDense`、`fillSuppressed`、`fillSuppressionReason`、`recentAppendCount`、`refreshIntervalMs`、`drawMs`、`nextFrameDelayMs` 和 `frameDelayMs`。其中 `nextFrameDelayMs` 是第一次后续 rAF 的延迟，`frameDelayMs` 还包含请求以来的实际帧间隔；历史仍以 512 项为上限。`fillSuppressionReason` 为 `severe-frame`、`persistent-slow-frame` 或 `large-batch-slow-frame`，未抑制时为 null；`recentAppendCount` 从上次主图提交计数，导入或预载历史不计作实时新批次。这些指标只参与显示调节，不影响采样、CSV、统计或能量积分。

2026-10-02 本机无界面 Edge 154 对实际 `chart.js`/uPlot 测量了 24 组样本：1 万、10 万、100 万点，3/8 通道，平稳、单点尖峰、快速交变信号；另覆盖 600/2400 CSS 像素宽与 DPI 1/1.5/2。最终矩阵每组预热 2.5 秒、测量 2 秒，全部原始追加点和尖峰保留，无页面异常；帧间隔 p95 最大 32.6 ms。10 万点、3 通道交变信号的单独对照中，固定 1 像素/桶且开启 15% 填充的策略约为 549 ms，而自适应策略约为 16 ms；固定策略仅模拟旧显示设置，不代表旧版本完整代码。早期矩阵和该对照的详细报告为不入库的 `bench/results/adaptive-chart-browser.json`，最终矩阵为 `bench/results/final-browser-matrix.json`。

这些是短时、合成、同机数据，不能代替 WebView2 持续录制验收。真机按 100/1000 次每秒分别持续至少五分钟，记录实际采样率、序号错误、原始点数、密度扩档与输入延迟；本机目标为帧间隔 p95 ≤33 ms、交互响应 p95 ≤50 ms，绝对耗时不作为共享 CI 门禁。

初期真机运行的输入 p95 超过 200 ms，还出现过约 400 ms 的呈现长帧；后续原生截图确认桌面锁屏，即使 `document.hidden` 为 false、`document.hasFocus()` 为 true 也不能据此确认前台可见。首次解锁复测也再次被锁屏中断。这些运行不能作为前台交互验收结论，历史报告保留于 `bench/results/adaptive-chart-webview2.json` 和 `bench/results/deliverable-interrupted.json`。禁用 DirectComposition、加速 Canvas、GPU 的实验没有改善该环境问题，未写入发布配置。

## 启动测量限制

`bench/startup.mjs` 的绝对毫秒只适合在同一批次、相同构建和相近主机状态下比较。记录结果时保留运行环境和主机探测值，避免把一次启动读数解释成跨平台保证。启动 benchmark 按需手动运行，不作为浏览器自动回归。

前端标记分别记录 `uiReady`（设置及平台信息生效、页面初始化完成）、`listenersReady`（采集及协议监听完整注册）、`devicesScanned` 和 `recoveriesScanned`。`appReady` 仍需页面、关闭监听、设备监听和设备扫描全部完成，不以提前挪动完成标记表示启动加速。监听失败时保持连接按钮禁用；异常记录扫描不阻塞 `appReady`。

## CI 与手动验证

CI 固定运行 `bench/packaging.mjs`、`bench/core.mjs --verify-baseline` 和报告型算法/Rust benchmark。性能优化开发者可按需运行：

```bash
npm run build
node bench/packaging.mjs
node bench/core.mjs --verify-baseline --output bench/results/verify.json
node bench/core.mjs --compare
node bench/phase2.mjs
node bench/phase3.mjs
node bench/extrema.mjs
node bench/startup.mjs
cargo bench -p lapower
```

真机检查仍可由维护者在目标设备上手动执行，但不属于托管 CI 的固定回归链路。详细的测试新增规则见 [开发与构建：测试与回归边界](DEVELOPMENT.md#测试与回归边界)。
